## Harness-given facts (do not score)

- Fixed virtual clock: every frame advances game time by exactly 16 ms; frame 0 is the first frame after Level 4 starts; trace line f = state at end of frame f (SCENARIO_FORMAT.md).
- time() returns time_seed + floor(virtual seconds since level start); level start = creation of the game layer (SCENARIO_FORMAT.md).
- std::random_device draws = high 32 bits of a splitmix64 stream seeded with device_seed at level start (exact algorithm given) (SCENARIO_FORMAT.md).
- These are the only entropy sources; mapping to srand/rand/C++ engines is left to the agent (SCENARIO_FORMAT.md). The mapping itself is rubric material (R42-R47).
- Bot plant action input timing: move to card (105, 1008 - 103*i) at F, press F+2, release F+3, move to cell centre (570 + 122c + 61, 110 + 140r + 70) at F+4, press F+14, release F+15 (SCENARIO_FORMAT.md).
- Design 1920x1080 bottom-left origin vs window 1280x720 top-left; wx/wy conversion formula (SCENARIO_FORMAT.md).
- Sun-collect bot: on frames G > 0 with G % N == 0, picks the first en=1 sun from the previous trace line that lies strictly inside the window; move at G, press G+2, release G+3 (SCENARIO_FORMAT.md).
- Run stops at end_frame or 60 frames after the game decides the result; the program may stop on its own and the trace then ends at its last written frame (SCENARIO_FORMAT.md). The fact that it does stop on a loss (abort) is rubric material (R49).
- Trace field names and meanings, number formatting, ids not scored, list order not scored, p.r = column and p.c = row as stored (TRACE_SCHEMA.md).

## Notes: what could not be read directly from source, and how it was resolved

- **Argument evaluation order.** C++ leaves the order of `rand()` calls inside one argument list unspecified (`Vec2(4+rand()%3, 16+rand()%5)`, `JumpBy(..., Vec2(rand()%120-60,0), rand()%100+100, ...)`). I checked it against the public traces with glibc `rand()` (ctypes) and the reconstructed call count: both are left to right in this build. Sky sun at public-01 f314 is rand index 51 → x 1510 and dx -17 (index 52). Sunflower timers at rand index 18 give (6 s, 18 s) for public-02 and (6 s, 17 s) for public-03, matching the observed first-sun delays and periods.
- **Input vs. tick order within a frame.** The source alone does not show when GLFW mouse events land relative to the scheduler. I took it from the cocos main loop (`mainLoop()` then `pollEvents()`) and confirmed it with the rand index: the 0.1 s tick at f64 runs before the card pick-up processed in f64.
- **Scheduler phase.** The cocos `Timer` skips its first update and accumulates float32 dt. I simulated this and it reproduces every observed tick: card `en` flips at f8/545/1008/1108/1526/1664/3833, wave-timer changes at f64/127/189…, sun deletions at f751/876. Accumulation effectively starts with frame 2's dt. This is stated as frame numbers, not derived from first principles.
- **Spine animation timing** (eat bites, pea shots, zombie fall/die) comes from the shipped `.compiled` spine JSON: Eat 1 s with the bite event at 0.5 s, Shoot 1 s with the shot event at 0.5 s, Die with filldown at 0.4989 s and die at 1.1333 s. These are combined with the random timescales. The per-zombie engine model (seed from the k+1-th device draw, one draw per frame for the groan check) predicts 98.8 / 81.6-frame bite periods and a 39.7-frame fall delay. Observed values are 99 / 82 / 41. Without the per-frame draws the fall delay would be about 30 frames, so the per-frame consumption is confirmed. Event dispatch adds about 0-1 frame of quantisation, so timing rules accept ±2 frames.
- **Engines and distributions** (minstd_rand0, libstdc++ `uniform_int_distribution` downscaling, single-draw `uniform_real_distribution<float>`) are libstdc++ facts, not project code. I verified them by reproducing every public spawn x and lane exactly (seeds 101/102/103).
- **Loss threshold.** `GAMEWORLD_1DATAS.json` says `UserLose: 430`, but `LevelDataHandler::createLevelDataFromDocument` never reads it, so `LevelData.userLose` stays 0 (x < 0). Confirmed: every losing trace (hidden-01/07/08, cal-04) ends with the lead zombie at 0.09-0.41.
- **Crash.** I matched the abort path from source against the operator's stdout logs ("Zombies Win" then "*** buffer overflow detected ***", rc 134). The win path calls the same buggy function and should abort the same way, but no trace reaches a win, so R50 is inferred (weight 1).
- **Not determined exactly:** the sun skeleton's bounding-box size for click hit tests (it only matters for overlapping suns and off-centre clicks; the bot clicks the centre), the exact uniform_int rejection frequency (probability ~5e-7 per draw, ignored), and whether coin pickups can interfere (coins are not traced; a sun click over a coin would also collect the coin, which has no scored effect). Cosmetic-only state (skins, sounds, flags, progress bar) is deliberately left out.
- **Tier assignment** comes from checking the three public traces. No bucket zombie and no shield damage appears there (R17/R18 are tier 2), and neither does a refund/cancel (R07, seen only in cal-03), a shovel event (hidden-05/07/08), a wave beyond 3 (R40) or a loss (R48/R49). Hidden and calibration traces were used only to confirm values.
